# Architecture

site-forge is a **registry** (this repository) and a **CLI** that copies from it. It is not a
framework: nothing from site-forge runs in a generated site except code that was copied into it
and now belongs to that site.

```
registry/                         packages/cli                    my-site/ (your repo)
├─ core.json  ── starter + slots ─┐                              ├─ site.config.ts
├─ modules/*/module.json + files ─┼─► resolve ─► copy ─► generate ─► ├─ src/…            (copied, yours)
├─ sections/*  ui/*  themes/*   ──┤   (requires,  (hash    (slots,   ├─ src/generated/*  (CLI-owned)
└─ presets/*.json + page files ───┘    conflicts)  every    env,     ├─ src/env.ts       (CLI-owned)
                                                   file)    config)  └─ .site/manifest.json
apps/starter  (the skeleton every site begins from)
apps/playground (generated: every module at once, for testing)
```

## The pieces

| Piece                                  | What it is                                                                                                                                                                                                  |
| -------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Starter** (`apps/starter`)           | A complete, minimal Next.js app: layout shell, theme tokens, metadata helpers, security headers, 404/500, env validation, `site.config.ts`. Every project starts as a copy of it.                           |
| **Module** (`registry/modules/<name>`) | A feature: `module.json` + `files/` (mirroring project paths) + `README.md`. Declares requirements, env vars, dependencies, DB schema, routes, nav entries, `site.config.ts` blocks and slot contributions. |
| **Section** (`registry/sections`)      | A page section (hero, pricing table …): props in, markup out, styled only with semantic tokens.                                                                                                             |
| **UI primitive** (`registry/ui`)       | Buttons, fields, dialogs … (Radix-based where behaviour is non-trivial).                                                                                                                                    |
| **Theme** (`registry/themes`)          | A `theme.css` of dial values plus font choices.                                                                                                                                                             |
| **Preset** (`registry/presets`)        | A named selection of modules, sections and a theme, plus page files (e.g. the home page) that compose them.                                                                                                 |

All manifests are validated with Zod schemas in `packages/cli/src/schema/manifest.ts`; JSON
Schemas in `registry/schema/` give editors autocomplete.

## Resolution

`resolvePlan()` expands a selection with every `requires` (transitively), pulls in the sections
and primitives modules list, orders modules so dependencies come first, and rejects conflicts
and cycles. The same resolver drives `create`, `add` and `update`.

## Slots: integration without imports

Modules never import optional modules. Instead, a module that wants to extend another
**contributes to a slot**, and the CLI generates the glue:

```json
{ "slot": "sitemap", "import": "blogSitemap", "from": "src/lib/blog/sitemap.ts" }
```

becomes, in `src/generated/sitemap.ts`:

```ts
// @generated by site-forge — do not edit. Run `pnpm site sync` to regenerate.
import { blogSitemap } from "../lib/blog/sitemap";

export const sitemapSources: (() => MetadataRoute.Sitemap | Promise<MetadataRoute.Sitemap>)[] = [
  blogSitemap,
];
```

Slots are owned by the starter (`providers`, `body-end`, `header-actions`, `next-plugins`,
`proxy`, `html-lang`, `error-reporters`) or by modules (`auth-plugins`, `auth-events`,
`dashboard-widgets`, `payment-webhooks`, `email-templates`, `onboarding-tasks` …). A
contribution to a slot whose owner isn't installed is skipped, so installing modules in any
order, or removing one, always leaves a consistent project.

Other generated files follow the same idea: `src/env.ts` extends every module's Zod env fragment,
`src/generated/db-schema.ts` collects Drizzle tables, `src/generated/next.ts` merges CSP sources
and image hosts, `.env.example` documents every variable, and `pnpm-workspace.yaml` lists which
dependencies may run install scripts. `site sync` rebuilds all of them offline.

## The project manifest

`.site/manifest.json` records, for every installed item, a **snapshot of its manifest** and the
**sha256 of every file** at install time. That is what makes the CLI safe to use on a project
you've been editing for months:

- `site add` / `update` never overwrite a file whose hash changed (you edited it) unless you pass
  `--overwrite`;
- `site remove` deletes only untouched files, and hands edited ones over to you;
- `site diff` tells "updated upstream" from "changed by you";
- `site sync` and `site remove` work offline, from the snapshots.

## Design tokens

Everything visual derives from a few **dials** in `src/styles/theme.css` (hue, tint, accent,
radius, density, shadow, motion, type scale, measure). Semantic tokens (`--background`,
`--primary`, `--muted-foreground` …) are computed from the dials in OKLCH, for light and dark.
Components only use semantic utilities (`bg-primary`, `text-muted-foreground`), which
`scripts/validate-registry.ts` enforces. See [theming.md](theming.md).

## Development without keys

Every module works locally with zero configuration, and switches to the real service when its
env var appears:

| Concern     | Without keys                                | With keys             |
| ----------- | ------------------------------------------- | --------------------- |
| Database    | Embedded Postgres (PGlite) in `.site/dev`   | `DATABASE_URL`        |
| Email       | Outbox at `/dev/outbox`                     | `RESEND_API_KEY`      |
| Payments    | Mock checkout and portal at `/dev/checkout` | `STRIPE_SECRET_KEY`   |
| Uploads     | Local disk through the app                  | `S3_*`                |
| Rate limits | In memory                                   | Upstash Redis         |
| Newsletter  | Logged                                      | `NEWSLETTER_PROVIDER` |

Production refuses to start without the variables marked `required`, and `pnpm env:check` /
`site doctor --production` say exactly what's missing.

## Quality gates

- `pnpm validate`: manifests ↔ files, import isolation (a module imports only the starter,
  itself, its `requires`, and its declared sections/primitives), env fragments, token rules,
  README sections, explicit DB column names, no TODOs, no duplicated starter dependencies.
- `pnpm check`: typecheck, lint and unit tests for every workspace package.
- **Playground**: every module generated together, typechecked, linted, built and exercised by
  Playwright (functional flows plus axe accessibility checks in light and dark).
- **Presets**: each preset (and the bare starter) is generated with the CLI into an empty
  directory and must install, typecheck, lint and build on its own (`pnpm build:preset`), on
  every change and weekly.
